## Probes that passed (no finding)

- **Schema applied before migration.** `openDatabase` runs `hasIntegerIds` → migrate → `applySchema`, so the new `schema.sql` never runs against an old table on the normal path. If it ever did, it would still succeed: `CREATE TABLE IF NOT EXISTS` is a no-op, and `idx_todos_created_at` references `created_at`, which already exists. The migration's `DROP INDEX IF EXISTS` then removes the stray index. No failure mode.
- **RENAME and indexes.** With `legacy_alter_table=OFF` (the default), `ALTER TABLE … RENAME` carries the indexes over under their **old names**. Without step 1, `CREATE INDEX IF NOT EXISTS` would silently no-op and the new table would have no indexes. The design drops the indexes first, which is correct. `sqlite_sequence` is renamed with the table and cleaned up by `DROP TABLE`. No triggers, views or FKs reference `todos`, so `foreign_keys=ON` has nothing to do.
- **DDL in a transaction / WAL.** SQLite DDL is fully transactional, so `DROP INDEX`, `RENAME`, `CREATE` and `DROP TABLE` all roll back. `db.exec(schema.sql)` contains no `BEGIN`/`PRAGMA`, so it is legal inside `db.transaction`. `journal_mode=WAL` is set before the transaction. On `:memory:` the pragma returns `memory`, which is harmless.
- **`hasIntegerIds` on a fresh DB.** `find(...)?.type.toUpperCase()` short-circuits the whole chain, so it returns `false` without throwing.
- **`seed.sql` UUIDs.** 8-4-(`4`+3)-(`[89ab]`+3)-12 = 36 chars, lowercase. `random() & 3` yields 0–3 for negative values too (two's complement), avoiding `abs(INT64_MIN)`. `randomblob`/`random` are non-deterministic and evaluated per row. The output passes the strict v4 regex.
- **Ordering.** `toISOString()` and `strftime('%Y-%m-%dT%H:%M:%fZ')` produce the same fixed-width format. `(created_at, rowid)` is served by `idx_todos_created_at`. Inserting in `id ASC` order during migration preserves ties. The VACUUM caveat (R1) is correctly scoped to ties.
- **Duplicate detection.** The PK constraint inside a single `INSERT` is atomic. There is no check-then-insert window.
- **Dual-export under indirect eval.** In jsdom tests `module` is a wrapper parameter, not a global, so `(0, eval)` sets only the global. The `require` path in node-env tests is what produces coverage. This is sound.
- **XSS / injection.** The notice uses `textContent` and contains only numbers. Titles keep `textContent`. `data-id` goes through `dataset`. Ids are regex-validated before the `409`/`404` messages echo them. All SQL uses bound parameters, and client URLs use `encodeURIComponent`. No new secrets or hosts, and no dependencies.
- **Storage edge cases.** A failed write-back (step 4) imports nothing and leaves the original key, so the next load retries. A failed write of the remaining items still leaves the full written-back list with stable ids, so the retry produces `409`s and no duplicates. A failed `removeItem` only causes one repeat "Imported N" notice.
- **Simplicity.** Two small frontend modules (one pure, one orchestration with injected I/O) are justified by C2. The hand-written single migration, the injected `newId`, and the absence of a migration framework or `seq` column are all proportionate. Only D-9 is unnecessary code.

## Traceability gaps

- **EH-4.** The "400 other than an invalid entry, so stop" branch is not designed (D-1). This is the only requirement not met.
- **NFR-5.** Coverage is measured by hand, and `main.js` wiring is not measurable (D-5, R3 needs human confirmation).
- **FR-4 "id never changes".** This can be violated by concurrent migration (D-2).
- Every other FR, EH, NFR and AC maps to a component and a named test in §10. I found no unrequested scope.

## Strengths

- The constraints table (§1, C1–C6) is grounded in the real code, e.g. `clearMessage(els.appMessage)` on load, the eval/coverage limits, and the shared seed timestamp.
- The rename-old-first migration keeps `schema.sql` as the only DDL. The index-name clash is identified and handled explicitly.
- `NOT NULL` on the TEXT PK (SQLite's NULL-in-PK quirk) and no SQL default for `id` are deliberate and correct.
- `LegacyImport.run` is pure orchestration with injected storage, api and model, and it never rejects. It is easy to test exhaustively in node env.
- The "zero fetches when no legacy key" property keeps existing call-counting tests valid.
- The test strategy names concrete fixture shapes: equal `created_at`, id gaps, and reopen with raw better-sqlite3 for EH-8.
